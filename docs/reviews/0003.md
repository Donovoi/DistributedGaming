# Remote capture environment review

Date: 2026-11-24.

Scope: a remote 64-bit Vulkan capture environment. No game milestone closes. Progress stays at 20%.

## Round 1: design challenge

An independent reviewer challenged the setup before completion.

| Finding | Response |
| --- | --- |
| i386 runtime libraries could be mistaken for 32-bit RenderDoc support. | State that Linux capture is x86-64. Require inspection of the actual game binary. |
| GPU access alone could hide software rendering. | Check GLX and Vulkan inside the final container. Capture a real draw and inspect the saved output. |
| A test display could disturb an existing session. | Use a separate display, private Xauthority, no TCP, no input devices, and no VT switch. Run the container as the user. |
| Apt packages are not pinned. | Record this limit, source identities, image ID, and package inventory. Do not claim a fully repeatable release. |
| Building Python bindings does not prove they load. | Check the import as the intended user, then use the API for capture and replay. |
| Setup could be mistaken for M3 completion. | Keep M3 pending. Require a separate real game baseline and capture. |

## Round 2: implementation and evidence challenge

The second reviewer found that counting distinct bytes could accept a flat image when each color channel had a different value. The script now checks the four-byte pixel layout, exact data length, and whole pixels. A regression test covers that case.

The reviewer found no further source or privacy blockers. The final script then passed its four regression checks and a new capture/replay run on the remote GPU. Its hash and result were updated in the validation record. A check also confirmed that an existing report cannot be overwritten.

The resource handoff record states that capture containers were removed, the test display remains for separate Steam setup, and paused GPU services were restored. Required CI checks must pass for the final PR head before merge.
