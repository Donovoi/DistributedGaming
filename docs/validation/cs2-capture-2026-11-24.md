# First Counter-Strike 2 capture

Date: 24 November 2026. Location: remote PC A. Repository base: `70ffac04a2dd194bd85139e96a4e995c8707a389`.

## Result

Captured one real game frame from a local SourceTV demo. Replay produced a visible world scene on an RTX 3070. The image contains the map, lighting, and HUD. Repeated replay did not match every byte. This is capture evidence, not a correct pass replay or a game speedup. M3 and M4 remain pending. Progress stays at 20%.

The [machine record](cs2-capture-2026-11-24.json) pins the inspected executable, demo, capture, runtime, and capture tools. These hashes identify selected files. They do not prove full Steam file integrity. Raw captures, demo files, images, and account data stay private.

## Method

1. Install the game through the signed-in Steam client on the remote PC. Inspect the actual executable. Require ELF64 x86-64.
2. Launch with `-insecure`. Before instrumentation, inspect the process arguments and confirm the local game's `VAC secure mode disabled` message. Use a local listen server with `sv_lan` enabled. Record a SourceTV demo of `de_dust2`. Do not enter matchmaking.
3. Run the game inside Steam Linux Runtime 3.0, code name sniper. Build RenderDoc 1.47 from source commit `b0e1370309f7d7bf986a73830446ca39d9b8c1fd` in the pinned sniper SDK. The source worktree was clean when checked. Enable Python bindings and the command tool. Disable the Qt front end. Use a Release build. The version command omitted the Git hash, so record the source commit and library hashes separately.
4. Point the implicit Vulkan layer at that build's `librenderdoc.so`. Use its Python module in the same runtime. Inject the final game executable with RenderDoc's `ExecuteAndInject`. Retain `-insecure` in the capture launch. The earlier Ubuntu build failed the runtime's library requirements and was not used for this capture.
5. Play the private SourceTV demo. Disable the auto director and TrueView prediction. Select the spectator camera shown in the machine record. Pause playback and hide the demo controls. Inspect the world scene before requesting one frame. The camera readback was near the capture request; no frame-to-console tick link was recorded.
6. Open the capture on the same remote GPU. Walk the action tree. Select the final present event and read its color image with `GetTextureData`. Rewind to event zero, return to the present event, and read the image again. Compare all returned bytes. Inspect a saved image for actual world geometry.

The first inspection counted 2,670 actions, including 1,577 draw actions and 19 dispatch actions. It listed 4,999 textures. These are API action and resource counts. They do not establish independent tasks or a complete dependency map.

The present image is 1920 by 1080, with format `B8G8R8A8_SRGB`. The launch requested 1280 by 720, but the borderless output used the display size. Use the observed size. Present size alone does not establish every internal rendering resolution.

RenderDoc reported `degraded: false`. This reports its replay status only. It does not certify output correctness. The non-flat image check compares pixels within one image. The separate repeat check compares complete readbacks from separate replays.

The first inspection retained one image hash and the failed equality result. It did not retain the second hash. A follow-up opened the same capture with two replay controllers and retained four full readbacks. The first controller's two outputs matched. The second controller's outputs differed from the first output by 98 and 28 pixels. The largest byte-channel differences were 9 and 6. These are small differences, but the acceptance check is still unresolved. The cause is unknown. No tolerance was added to turn the failure into a pass.

## Limits and next checks

The private capture helpers are experiment tools, not a released adapter. They ran outside the Rust harness. The sniper SDK image is pinned, but packages installed during the build are not fully pinned. A second operator has not repeated this setup.

Separate preliminary timing runs completed after a warmup. They used MangoHud, a fixed spectator camera, and a fixed demo interval. Final output-size and loaded-library checks were not completed before the isolated X server's time limit ended the session. Do not use these runs as accepted baseline evidence. Repeat with those checks and retain timing boundaries for review. Input delay and display delay were not measured.

The remote GPU worker was stopped under the user's standing permission. A restore timer bounded the stop. The worker was restored and confirmed active after the test burst. A service on another PC was already inactive before this burst and was left in that state.

Next, accept a clean baseline with fixed settings. Then explain the replay difference, trace resource reads and writes, and check one pass in isolation. Do not count a visible image as verified output.
